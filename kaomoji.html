顔文字の構成が、そのまま戦い方になる

Kaomoji Clashは、顔文字を引っ張って射出し、敵との衝突で戦うビルド主導型アクションです。戦闘で得た記号パーツを組み替え、パーツの成長値とタグ効果から次のビルドを作ります。

装備中パーツの構成・レベル別補正・タグ効果からSpeed・Power・Guard・Staminaを算出します。操作はドラッグとリリース。狙う方向と引く距離を決め、壁の反射も利用して敵への再接触を狙います。

戦闘とビルドのループ

Waveを攻略して得た報酬を、パーツの入手・成長と次の構成に結び付けます。

  1. エリアを選ぶ難易度を選択して戦闘へ。
  2. 引いて射出するドラッグ方向と距離を決め、敵にぶつける。
  3. Waveを攻略する敵を倒し、パーツ・経験値・報酬を得る。
  4. 顔文字を組み替える所持パーツを選び直し、異なる構成で次の挑戦へ。

CORE SYSTEMS

この作品の4つの見どころ

01

顔文字パーツで性能を組み立てる

5つのスロットに設定したパーツのうち、目と口は顔文字表示に使い、全パーツからステータス補正とスキルタグを集計します。

02

タグの重なりを効果へ変換する

同じタグを最大5スタックまで集計し、スタック数ごとに用意した補正値を適用。条件付きタグは衝突時の効果に使います。

03

引く距離を発射速度に結び付ける

ドラッグの方向と距離から速度を計算し、物理衝突後は反射と速度差をもとにダメージを判定します。

04

連続命中とWave報酬をつなぐ

連続して敵にダメージを与えるとコンボが伸びます。3つのWaveからなる戦闘の終了時にパーツを所持品へ加え、装備中パーツに経験値を反映します。

ビルド計算：スロットから戦闘ステータスまで

パーツは見た目の記号だけではなく、レベルに応じた4種の補正値とスキルタグを持ちます。ビルド画面ではパーツの種類を選び、選択したパーツのステータスとタグを確認できます。

スロットビルド内の役割現在の処理
目・口顔文字の見た目と性能を構成目は左右に分割し、口と顔の輪郭をつないで文字列化
手・装飾1・装飾2顔文字表示とは別に性能を構成表示用文字列には含めず、タグとレベル別ステータスを集計

ステータス集計は、装備中の各スロットからパーツの補正値を合算します。スロット別倍率による重み付けは行わず、未装備スロットはスキップします。

  1. パーツデータを選ぶKaomojiPartDataが部位、記号、レベル別の補正、スキルタグを保持。
  2. 顔文字とタグを集めるKAOMOJIが5枠をまとめ、表示用の顔文字とタグ一覧を作る。
  3. タグを分類・集計するPlayerUpgradeServiceが通常タグと条件付きタグを分け、重複数をそれぞれ最大5まで数える。
  4. 補正を順に適用する通常タグの効果を適用した後、各パーツのレベル別補正値を合算してステータスへ反映。
  5. プレイヤーへ反映するPlayerApplyKaomojiが全パーツのタグをPlayerUpgradeServiceへ渡し、顔文字表示と文字数に応じた当たり判定幅を初期化。移動・戦闘処理は計算済みステータスを参照。

タグ補正はスタック数ごとに設定

UpgradeDefinition.csのSkillTag（ScriptableObject）は表示名、条件付きかどうか、最大スタック数と各段階の補正を保持します。PlayerUpgradeServiceは集計したスタック数に対応する補正を取得します。

乗算してから加算

各タグのStatusModifier.ApplyModifierは「現在値 × mul → addを加算」の順に処理します。タグ補正を適用した後、パーツ補正は「現在値 ×（1 + パーツ補正合計）」として反映します。

条件付きタグは別経路

条件付きタグは常時ステータス補正から除外されます。たとえばReboundBoostは壁との接触時にレベル別の速度倍率・時間を取得し、一時的な速度上昇と残像表示につなぎます。

戦闘処理：ドラッグから命中まで

プレイヤーの操作はタッチドラッグです。引いた距離が短すぎる場合は発射せず、距離に応じた速度でRigidbody2Dを動かします。

  1. 方向と距離を決めるPlayerMovementがタッチ位置をワールド座標へ変換し、ドラッグ距離を上限内に収める。
  2. リリースして発射最小距離を満たすと、方向・距離の割合・プレイヤーSpeedから初速を計算。
  3. 物理衝突で反射Reflectが衝突面の法線で速度ベクトルを反射し、reflectPowerを適用。
  4. 速度差でダメージ判定PlayerReflectはプレイヤー側の速度が敵側を基準とした閾値を超えた場合にダメージを与える。
  5. 命中結果を反映Comboは3秒の継続時間と最大10コンボを使って攻撃倍率を補間し、敵の体力、ヒットストップ、効果音へつなぐ。

攻撃の強さを「当て方」に結び付ける

プレイヤーと敵の双方が同じReflect基底処理で衝突方向を反射し、ダメージ条件はそれぞれの派生クラスで判定します。プレイヤーは反射後の速度の二乗が敵側の0.92倍を上回るとダメージを与え、その命中時だけコンボを加算します。

主なクラスとデータのつながり

ビルドとステータス

KaomojiPartDataがパーツ単位の記号・補正・タグを保持。KAOMOJIが装備枠をまとめ、PlayerApplyKaomojiがタグを渡して表示と当たり判定を初期化し、PlayerUpgradeServiceがステータスを計算します。

入力と戦闘

PlayerMovementがタッチ入力と発射、Reflectが共通の物理反射、PlayerReflectがプレイヤー側のダメージ条件・コンボ連携を担当。

進行と報酬

BattleFlowManagerが接敵・戦闘開始と終了を進行。WaveControllerがWaveを順に処理し、DropControllerとResultControllerがパーツ報酬・所持品・装備パーツの経験値を扱います。

実行時のパーツ一覧はKaomojiPartsManagerがResourcesから読み込み、部位ごとにキャッシュします。顔文字ビルド画面は部位別に一覧を表示し、選択したパーツの数値とタグをプレビューします。

実装の詳細と設計判断

実装の仕組みと、その構成にした理由をまとめています。実装は実際のコードやコミットの内容、振り返りは今コードを読み返して考えていることです。

ステータス計算を「タグ補正→パーツ補正」の2段階にした理由

実装PlayerUpgradeServiceでは、まずApplyTagEffectsでタグ補正（現在値×mul＋add）をかけ、そのあとApplyPartsEffectsでパーツ補正を「現在値×（1＋補正合計）」として重ねています。

// StatusModifier
float v = ApplyMultiplication(baseValue);  // × mul
return ApplyAddition(v);                   // + add

// PlayerUpgradeService
UpgradedStatus.speed += UpgradedStatus.speed * GetTotalParamByType(StatusType.Speed);

振り返りパーツ補正は足し合わせた値を掛けるので、枠が増えても伸び方が緩やかです。一方のタグ補正は、スタック数ごとに決めた段階で効きます。この2つを分けることで、「ビルドの方向性はタグ、細かい強さはパーツ」と役割を分けて調整できます。パーツ補正は−0.2〜0.2の範囲で設定でき、デメリット付きのパーツも作れます。

別の方法を選んだ場合

補正をすべて「加算・乗算・最終」の種類を付けたリストにまとめ、優先度順に一括で適用する方法もあります。調整やデバッグはしやすくなりますが、実装は大きくなります。ステータスが4種類、タグも少数だったため、今の2段構成で十分だと考えています。タグを先に適用する順序にした理由は、当時のコードやコミットに記録が残っておらず、はっきりしません。

SkillTagをScriptableObjectで段階別データにした設計

実装SkillTagは抽象クラスのScriptableObjectです。条件付きかどうかを示すisCondition、最大スタック数maxStacks、スタック段階ごとのStatusModifierのリストを持たせています。説明文を返すGetDescription(stack)も同じクラスに置いています。

振り返り数値と説明文を同じ場所に置いたので、補正値を変えても表示とずれにくくなります。段階ごとの数値はコードを触らずにInspectorで調整できます。CSVなどの表データにする方法は差分を追いやすい反面、Unity上で参照を確認しにくくなるため、ScriptableObjectにしています。

今の実装の弱点

集計の上限はPlayerUpgradeService側で5と決め打ちしていて、SkillTag.maxStacksとは別に管理しています。maxStacksが5未満のタグを作ると範囲外を参照する可能性があるので、上限はSkillTag側の値に揃えたいと考えています。

Waveの敵・ドロップ・報酬を戦闘前に確定する設計

実装WaveController.CreateWaveDataで、戦闘に入る前に3Wave分の敵、ドロップ、獲得金、経験値を決めています。敵の数は、難易度ごとの基準数からceil(基準×(1＋0.6×Wave番号))で増やしています。EnemyDataは生成時にコピーして使い、元のScriptableObjectは書き換えません。

振り返り先に決めておけば、戦闘中に乱数が変わらず、結果の集計も単純になります。撃破のたびに抽選する方法はデータが軽くなりますが、戦闘前の予告表示やテストがしにくくなります。

衝突ダメージの閾値と、調整履歴（コミットb0b123e）

実装プレイヤーがダメージを与える条件は、反射後の速度の二乗が、敵側の速度の二乗×0.92を上回ることです。二乗のまま比べているので、平方根の計算は要りません。

コミットb0b123e（衝突判定をもっと緩やかにした）で、プレイヤー側の係数を1.0から0.92に、敵側を1.2から1.0に変えました。これでプレイヤーが少し遅くてもダメージを与えられ、敵はプレイヤーと同じ速度でも攻撃できます。

振り返り「速いほうが当たり勝つ」を1つのルールで表せるので、引いた距離がそのままダメージに結び付きます。質量も含めた運動量で判定する方法もありますが、「引いた距離＝強さ」という分かりやすさが薄れるので採っていません。0.92という値を選んだ根拠は、コードには残っていません。

PCのマウス操作からモバイル専用タッチ操作への移行

実装コミット1db96a4で、入力をタッチ専用にしました（PCのマウスでは操作できなくなります）。PlayerMovementでは、ドラッグ距離を上限に収めたあとfreeDragMaxDistanceRateで補正して、発射の強さを決めています。引く距離が最小値に満たないときは発射しません。

振り返りスマートフォンでは、指で長く引ける距離に限りがあります。画面の端まで引かなくても最大の強さに届くよう、補正率を調整できる形にしたと考えています。実機での操作感を数値で測った記録はありません。

不具合修正の例：UI Toolkitの名前解決失敗と、見えない失敗の除去（ff81edf）

問題

ホーム画面のパーツプレビューで、ステータスのProgressBarが更新されませんでした。

原因

UXMLのテンプレートインスタンスに名前を付けていなかったため、StatusParamater.Initializeでの検索結果がnullになっていました。しかもnullのときは何もせず戻る処理を入れていたので、失敗に気づけませんでした。

対応

UXMLにインスタンス名を付け、失敗を黙って見逃すnullガードを外し、確認用のログを足しました。

学んだこと

例外を避けるためのnullガードは、不具合を見つけにくくします。初期化に失敗したときは、気づける形で知らせるほうが原因を追いやすいと考えるようになりました。修正後の動作確認の記録はコミットには残していません。

現在のコードを読み返して見つけた改善点

実際に起きた不具合ではなく、今コードを読み返して気になっている点です。

  • タグ集計の重複：SetTagsとSetConditionTagsがほぼ同じ処理で、上限の5も別に持っています。1つにまとめて、上限はmaxStacksに揃えたいです。
  • 速度上昇の重複起動：壁に当たるたびに速度上昇のコルーチンを起動しているので、連続で当たると、先に終わった効果が後の効果を早く打ち切る可能性があります。実際に起きるかは測っていません。
  • ヒットストップの重なり：連続して発生すると、timeScaleが早く元に戻る可能性があります。
  • 毎フレームのUI更新：Combo.Updateが毎フレームUIに値を渡しています。値が変わったときだけ通知するほうが無駄がありません。
  • 連携の仕組み：クラス間の連携はシングルトンと参照が中心で、イベントやオブジェクトプールは使っていません。続編のReloadedでは、サービスロケータとインターフェースで整理し直しています。
