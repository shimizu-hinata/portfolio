# 工程04 — デザインシステムとサイト構造の設計

## 位置付け

この文書は、既存サイトをゲームプログラマー向けポートフォリオとして改善するためのデザイン・実装設計である。**今回はHTML/CSS/JavaScriptを変更しない。** 作品の事実・担当・掲載素材が未確認の項目はプレースホルダーとして扱い、確認前に公開文言や画像を確定しない。

## 1. デザイン方針と再設計の範囲

### 方針

「作品と実装を読み進めやすくする、落ち着いたゲーム開発ポートフォリオ」。作品自体の配色・世界観はゲーム画面に任せ、サイトのUIは中立な背景、明瞭な文字、控えめなティールのアクセントで一貫させる。装飾や動きより、作品名、本人の役割、制作状態、機能から対応コードへ進む順序を優先する。

### 方針判断：部分再設計

全面的なデザイン置換は行わない。現状のブラウザー表示で確認できる強みは、作品画像を含むカード、ティールのアクセント、白いコンテンツ面、PCの2列構成、狭い画面での1列化である。これらを維持し、ページ全体の視覚言語を新しく作り直す必要はない。

一方、トップ画面にはプロフィール説明に続いて「制作を通して取り組んだこと」の4カードと「今後伸ばしたいこと」の3カードが作品一覧より先に置かれている。これらの抽象的な説明・自己評価を短縮し、作品と本人の役割へ早く到達する情報階層へ改める。全体背景の色・模様は作品カードより目立たない強さに抑え、見出し・本文・メタ情報の小さな文字を読みやすくする。

### デザイン上の注意

- 現在のトップのヒーロー画像は `KaomojiClash_Thumbnail.png` を `ゲーム画面` とする代替テキストで表示しているが、実プレイ画面である証拠は未確認。作品画像と説明の一致を確認するまで、作品のプレイ画面を装う用途に使わない。未確認ならヒーロー画像なしのテキスト主導レイアウトにする。
- 既存画像を装飾目的に増やさず、各画像に「どの機能・場面を示すか」を付ける。ゲーム内画像の色味や比率は作品ごとに異なるため、カード全体をサイト色に着色しない。
- 「代表作品2件」は情報設計上の優先案であり、作品順位・制作情報・本人担当を確認後に最終確定する。工程1の証拠不足をデザインだけで補わない。

## 2. デザイントークン

値は実装候補の基準値。初期実装時に既存CSSとの競合とコントラストを確認し、用途ごとの場当たり的な値を増やさない。

### カラー

| トークン | 候補値 | 用途 |
|---|---|---|
| `--color-page` | `#F5F7F8` | ページ全体の薄いニュートラル背景。現行の強い色・模様を置き換える場合の基準 |
| `--color-surface` | `#FFFFFF` | カード、コード、画像のキャプション面 |
| `--color-surface-soft` | `#EAF3F2` | 小さな情報タグ、控えめな補助面 |
| `--color-text` | `#202A33` | 見出し、本文 |
| `--color-muted` | `#4D5B66` | 補足、日付、メタ情報。本文より弱くするが、小さすぎ・薄すぎにしない |
| `--color-border` | `#D6DEE3` | 区切り線、カード境界 |
| `--color-accent` | `#12655F` | 主リンク、主ボタン、状態を示す文字・アイコン |
| `--color-accent-hover` | `#0B514C` | hover時 |
| `--color-accent-soft` | `#E3F1EF` | 選択中タグ、リンク先強調の背景 |
| `--color-focus` | `#0B6E69` | キーボードフォーカス輪郭 |
| `--color-code-bg` | `#18232B` | コードブロック背景（コード掲載を確定したページのみ） |
| `--color-code-text` | `#F1F5F7` | コードブロック文字 |

ティール系は現行の既存アイデンティティとして維持し、主操作には白文字とのコントラストを確認した濃色を用いる。現行アクセント `#2ebaae` は薄い面や細い装飾線に限定し、小さい文字色や白文字ボタンの背景にそのまま使わない。意味を色だけで表現せず、ラベル・形・テキストも併用する。

候補値の相対輝度による計算では、白背景に対して本文 `#202A33` は14.58:1、補助文字 `#4D5B66` は6.99:1、アクセント `#12655F` は6.88:1、フォーカス `#0B6E69` は6.09:1、コード文字 `#F1F5F7` とコード背景 `#18232B` は14.57:1。通常サイズ文字4.5:1以上・大きな文字3:1以上を目標とする。これは指定した色ペアの計算値であり、実際に隣接するすべての面、画像上の文字、フォーカス輪郭や画面全体のアクセシビリティ監査を済ませた意味ではない。

### タイポグラフィ

- 日本語の本文はOS標準の読みやすいゴシックを優先し、外部Webフォントが使えない場合もレイアウトが崩れないフォールバックを用意する。現行のSource Sans Pro / Ralewayは既存テーマの表示との互換性を見ながら、英字見出し・小さなラベルに限るか段階的に縮小する。新たなフォント依存を増やさない。
- 本文候補：`system-ui, -apple-system, BlinkMacSystemFont, "Segoe UI", "Noto Sans JP", "Hiragino Kaku Gothic ProN", Meiryo, sans-serif`。
- コード候補：`ui-monospace, "SFMono-Regular", Consolas, "Liberation Mono", monospace`。
- 基準：本文 `1rem`、行高 `1.7–1.85`。補足文字も原則 `0.875rem` 未満にせず、文字間を過度に広げない。
- 階層（可変値の目安）：H1 `clamp(2rem, 4vw, 3.25rem)`、H2 `clamp(1.5rem, 2.5vw, 2rem)`、H3 `1.2–1.35rem`、本文 `1rem`、メタラベル `0.8–0.875rem`。
- 技術用語・英語タイトルは本文の読みやすさより優先しない。大文字化、字間、斜体を連続使用しない。

### 余白・幅・レイアウト

- 4px相当の基準に沿う一貫した段階値（`0.25rem`, `0.5rem`, `0.75rem`, `1rem`, `1.5rem`, `2rem`, `3rem`, `4rem`）を用いる。
- ページ内容の最大幅は `72rem` 程度。左右の余白は小画面 `1rem`、中画面 `1.5rem`、大画面 `2rem` を基準にする。
- 文章・コード解説の読幅は `65–72ch` 程度に制限し、長い段落を画面全幅へ広げない。
- 代表作品カードはPC 2列、狭い画面で1列。補足カードは一覧の密度に応じて2〜3列から1列にする。作品詳細は読み進める主カラムを一つにし、長い並列カラムや横スクロールを必須にしない。
- セクション間は `3–4rem`、カード内余白は `1.25–1.5rem` を基本とする。小画面では段階的に縮小する。
- `#projects` などのアンカー位置は固定ヘッダーに隠れないよう `scroll-margin-top` を設ける。現在のハッシュフォーカス演出は控えめな輪郭・短時間へ調整可能とするが、既存の未コミットCSS/JSをこの工程で変更しない。

### ブレークポイント

- `48rem` 前後：2列カード・ヒーローの左右分割から縦積みへ変更。
- `62rem` 前後：広い余白・補助列を切り替える。
- 既存サイトは `980px` / `736px` 付近のルールがあるため、実装では既存ブレークポイントを確認し、無理由に別体系を重ねず実際のレイアウト崩れが起きる幅で調整する。

## 3. 共通コンポーネント設計

| コンポーネント | 共通ルール | ページでの使い分け |
|---|---|---|
| サイトヘッダー／ナビ | 作品名またはポートフォリオ名、トップ・作品一覧・連絡導線。リンクは実在する相対URL。キーボードで操作可能 | 現行の共通テーマナビを活かし、詳細ページの繰り返しミニカードは整理する |
| ページ導入（Hero） | H1を1つ、短い説明、任意の主CTA。情報を先に出し、背景装飾は置かない | トップは制作者・ロールと代表作への導線。作品詳細は作品名と遊びの説明。画像は実物確認済みの場合だけ |
| セクション見出し | 見出し、任意の短い説明、階層を飛ばさないHTML見出し | 「Selected Works」等の装飾ラベルは補助とし、日本語の意味見出しを主にする |
| 代表作品カード | 実画面（ある場合）、作品名、概要1〜2文、確認済みの役割・個人/チーム・制作状況、詳細リンク。カード全面クリックと独立ボタンを重ねない | 代表2件を優先する案。情報確認前は役割・制作時期を空欄の事実として作らず、掲載項目自体を保留 |
| 技術ケースカード | 入力・処理・結果を一文で説明し、詳細ページ内の該当セクションへリンク | Algomate Colony / FingerDojoは短い技術事例として区分し、完成作と誤認させない |
| 開発中カード | 明示的な「制作中」表示、確認済みの差分、現在の状態 | Reloadedを完成作品と視覚・情報上分ける |
| 状態・役割タグ | テキストラベルを常に表示。色のみで状態を表さず、同じ語彙をサイト全体で使う | 「個人制作」「チーム制作」「開発中」等は本人確認後に表示 |
| メディア枠 | 実素材、統一した角丸と境界、適切なobject-fit、具体的なaltとキャプション | 証拠画像は対象機能・バージョンを確認。装飾画像は空alt。動画iframeはタイトルとレスポンシブ比率 |
| 技術説明ブロック | 見出し→画面または入力→処理の要約→ソースリンクの順。コードを読む人向け詳細は段階化 | 作品に必要な一事例を中心にする。クラス名一覧を置かない |
| コード抜粋 | `pre > code`、言語を明示し、短く、折り返しまたは局所横スクロール。コントラストとコピー可能性に配慮。ファイル名・行・外部ソースリンクを併記 | 実在し本人が説明できるコードに限る。画像とコードの対応をキャプションで示す |
| ボタン／テキストリンク | 主CTAは1つの塗りボタン、補助CTAは明確なテキストリンク。最低44px程度の操作領域を目標とし、focus-visibleを常に示す | ダウンロードCTAは実ファイル・権限・対象環境・到達性を確認後だけ |
| フッター | GitHub等の必要な外部プロフィール、連絡先（本人が希望・公開する場合）、コピーライト | 各詳細ページで同じ外部リンクの列挙を繰り返さない |

実装時は既存の `.portfolio-hero`、`.portfolio-grid`、`.minimal-card`、`.strength-card` 等を読み、適合するものは再利用・調整する。新しい別名クラスをページごとに作り、同じカードを二重実装しない。

## 4. ページ構造と視覚的な優先順位

### トップページ

```text
Header / Skip link
Main
  Intro: 氏名・ロール・短い紹介・代表作への主CTA
  Selected works: Kaomoji Clash / Bomb Crash（選定確定後）
  Technical cases: Algomate Colony / FingerDojo（短い補足）
  Additional works: 内容・公開状態を確認したサンプルだけ
  About / Contact: 簡潔に。確認済みのプロフィールだけ
Footer
```

ヒーロー直後に代表作品へ進める。現在の強み4カードは作品に裏付けられる文だけを代表カードまたは短い実装事例に統合し、「今後さらに伸ばしたいこと」3カードはトップの主導線から外す案とする。作品分類フィルターは、作品数・選定後に見つけやすさを改善する場合だけ残し、全作品を一覧で閲覧できる状態を維持する。フィルターを利用しないと作品が隠れたままになる設計にはしない。

### 代表作品・ケースページ

```text
Header / Skip link
Main (読みやすい単一カラム)
  Title + ゲーム概要 + 確認済みの制作情報
  実画面または実紹介動画（証拠がある場合）
  作品の中心機能（遊びの流れ）
  1つの実装事例（画面 → 処理 → 関連コード/データ）
  必要なソース・プレイ・補助資料へのリンク
  次作品への導線（必要な場合）
Footer
```

見出し名・説明量は作品ごとに変える。Kaomoji Clashはパーツとステータス計算、Bomb CrashはWave設定から敵出現まで、Algomateは命令の検証と逐次実行、FingerDojoはQTE倍率からダメージまでのように、資料で根拠を追える一つの経路に絞る。Reloadedは制作中であることと初版との差を先に示す。画像や動画に証拠がない項目を架空のビジュアルで補わない。

## 5. 操作・メディア・アクセシビリティ

- hoverは補助的にし、色・輪郭・下線・軽い移動など複数の手掛かりを使う。キーボードの `:focus-visible` はhoverより明瞭な輪郭で常時可視にする。
- `prefers-reduced-motion: reduce` では装飾アニメーションを停止または短縮する。既存のハッシュ遷移・スポットライト演出は、ページ読込後の予期しないスクロールや繰り返し移動を起こさないよう検証する。
- 画像には用途に応じた代替テキストを付け、内容を伝えない装飾画像は空altとする。キャプションは何が映り、何の機能と対応するかを短く記す。
- 動画は自動再生・音声再生を避け、iframeに内容を表すtitleを付け、16:9等の実比率を維持する。外部埋め込みに失敗してもリンクから内容へ移動できるようにする。
- コードの色だけに依存しない。小画面で長い行をページ全体に横スクロールさせず、コード領域に限定するか短い抜粋・外部ファイルリンクを用いる。
- `lang="ja"`、見出し階層、リンク名、ボタン名、色コントラスト、拡大表示、キーボード操作、タップ領域、画像・動画を実機相当のブラウザーで検証する。達成を先に断定しない。

## 6. サイト構造と実装方式

### 採用方針

**現行の静的HTML/CSS/JavaScriptとGitHub Pagesを維持する。フレームワーク、バンドラー、CMS、新しいnpm依存は導入しない。**

理由：

- 既存サイトはページ単位の静的HTMLで、作品ページごとに異なる内容・説明量を扱える。現在のタスクは情報階層と共通スタイルの整理が中心であり、ランタイムやビルドを増やすメリットが限定的。
- 現在のローカル構造には `package.json` 等の依存マニフェストやPagesのビルド手順が確認されていない。追加基盤は公開方式・保守コスト・相対パスに不要な変更をもたらす。
- コンテンツをHTMLのまま保つことで、公開先での生成処理に頼らず、既存のGitHub Pagesの静的公開モデルに適合させやすい。

### ソース・スタイルの扱い

- HTMLページは `index.html`、5つの作品ページ、旧URL互換ページ `single.html` を維持する。既存ファイル名・リンク先を変える必要がある場合は全内部参照と外部リンクを洗い出し、互換ページを消さない。
- CSSは現在の `assets/css/main.css` が `assets/css/modules/` を読み込む構成を維持する。デザインシステムのトークンは共通で一か所に定義し、トップと作品ページ共通の部品をモジュール内にまとめる。ページ固有ルールは既存の部品差分で表現し、同じ意味のスタイルを重複させない。
- Sassの `assets/sass/main.scss` は従来のHTML5 UPテーマのソースであり、現在のモジュールCSSと完全に対応しているか、生成・更新手順があるか未確認。工程5で先に由来を確認するまでSassをCSSのビルド元と見なさず、SassとCSSの両方を並行編集しない。CSSが実際の配信元なら、まずCSSモジュールを唯一の更新対象として扱う案とする。
- CSSは可能な限り共通トークンと既存部品を利用し、巨大な上書きファイルを積み増さない。既存CSSを整理する場合も、本プロジェクト開始前の変更を読み、別作業を巻き戻さない。
- JavaScriptは現在の `site.js` の共通処理、`portfolio-filter.js` のフィルターを維持し、HTML/CSSだけで実現できる表示のためのスクリプトを増やさない。フィルターを残す場合は `aria-pressed`、キーボード操作、絞り込み結果の通知、JavaScript無効時の全件表示を確認する。
- jQuery、HTML5 UP系スクリプト、Font Awesome、Google Fonts、YouTube等の既存依存は用途を把握したうえで変更する。デザインを整える目的だけでライブラリを更新・置換しない。

### GitHub Pages・URL

- `index.html`、`assets/`、`images/` 等を同じ配置のまま公開する。
- 内部リンク・画像・CSS・JavaScriptは `assets/css/main.css`、画像ファイルへの相対パス、`bombcrash.html` のような形式を使う。ドメインルート起点の `/assets/...` は使わない。`/portfolio/` 配下での公開とローカルプレビュー双方で機能することを確認する。
- ページ間リンク、作品アンカー、ソース外部リンクを変更した場合は全HTMLページから参照チェックを行う。`single.html` と既存の外部URLを不要に変更しない。
- GitHub Pagesの実際の公開元設定、指定URL `/portfolio/index.html` との対応は未確認であり、静的構成の設計だけでは公開先を確定しない。公開構成が相対パス前提に合うことを公開前に確認する。

## 7. 工程5（実装）の推奨順序と受け入れ条件

1. 公開元のPages設定と、CSS/Sassの配信・生成元を確認する。
2. 作品選定、担当・制作状態、画像・動画の出典・利用許可を確認する。根拠のないラベル・画像は保留する。
3. トークン、本文・リンク・フォーカス・カード等の共通スタイルを一度に整える。既存レイアウトの意図と未コミット差分を保持する。
4. トップページで自己紹介の反復を整理し、代表作→技術ケース→補足作品の順へ並べる。事実確認前のプレースホルダーを公開文に置かない。
5. 作品詳細を共通ナビ・コンテンツ幅・見出し・メディア・コード部品にそろえ、内容量は作品に合わせる。
6. ブレークポイント、内部相対URL、アンカー、フィルター、動画のフォールバックを検証する。
7. PCとモバイルの実ブラウザー表示、キーボード、縮小表示、コントラスト、読み上げ可能な名前を検証し、結果と環境を記録する。

**完了条件**

- デザイン方針とトークンが全ページに一貫している。色だけに意味を依存しない。
- 初めて訪れた人がトップから代表作、担当範囲、詳細へ迷わず到達でき、文章が画面幅に対して読みやすい。
- 各掲載画像・コード・機能説明の関係が説明でき、存在しない画面・未確認の成果・本人の意図を捏造しない。
- PC・小画面でナビ、カード、画像、コード、外部リンクが使え、横スクロールをページ全体に発生させない。
- GitHub Pagesの公開方式、相対URL、全内部リンク、画像、アンカー、フィルターの検証結果が記録される。
- 既存の未コミットCSS/JavaScript差分が保たれ、サイトに新しいビルド・ランタイム依存が不用意に追加されない。

## 8. この工程の実施結果
