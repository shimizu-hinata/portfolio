# 採用戦略と情報設計

## 目的と適用状態

採用担当者には短時間で「何を作り、本人は何を担当し、どの実物を見ればよいか」が分かり、エンジニアには必要な場合だけ根拠となる画像・コード・データの流れへ進める構成を定める。全作品のページを同じ長さに揃えず、作品の状態と証拠の量に応じて説明量を変える。

**構成案は本工程で確定。掲載順は [work-assessment.md](work-assessment.md) の証拠ベース提案とするが、担当・実行可能性・公開資料の確認までは、作品の事実を新たに断定しない。** 画像、コード抜粋、プレイ導線は現物・権限・本人確認が取れた場合のみ追加する。

## 情報の優先順位

1. 制作者の名前、志望ロール／強みの範囲、作品を見る入口
2. 代表作品のゲーム内容、本人の役割、制作状況、実物への入口
3. 作品ごとの具体的な技術事例と、その根拠
4. 追加作品・技術サンプル
5. 簡潔なプロフィールと連絡先・外部プロフィール

採用担当者は各代表作カードとページ冒頭・画面だけで判断できるようにする。コードを読む人だけが必要とするクラス名や呼び出し順は、代表文の中に羅列せず、1つの実装事例の内部に配置する。

## サイトマップ

```text
トップ /
├─ 制作者・強みの短い紹介
├─ 代表作品（優先2件）
│  ├─ Kaomoji Clash（初版）— 第一候補
│  └─ Bomb Crash — 第二候補
├─ 技術ケース／補足作品
│  ├─ Algomate Colony — コマンド実行の事例
│  ├─ 指道場（FingerDojo）— QTE戦闘の短い事例
│  ├─ 技術検証・小作品（確認後に選択）
│  └─ その他作品（必要な場合のみ）
├─ 開発中の記録
│  └─ Kaomoji Clash / Reloaded — 初版と区別した進行中のページ
├─ プロフィール・連絡先
└─ GitHub / note等の外部プロフィール

個別作品ページ
旧URL single.html（直接の主ナビゲーションには載せない互換導線）
```

「代表2件」は応募者の全制作物が2件という意味ではなく、最初の画面から深く読む対象を絞る編集上の判断。技術ケース、開発中の記録は完成作品と区別して引き続き紹介する。

### トップ各セクションの目的と掲載情報

| 順 | セクション | 閲覧者への目的 | 掲載する内容 |
|---|---|---|---|
| 1 | 制作者イントロ | 誰の何のポートフォリオか即時に伝える | 氏名、確認済みの希望ロール、短い強み、代表作への主CTA、GitHub等の副CTA |
| 2 | 代表作品 | 短時間で作品・担当・完成度を比較できる | Kaomoji Clash、Bomb Crash候補。タイトル、ゲーム概要、本人の役割、個人/チーム、状態、固有の技術ハイライト、詳細リンク。カード上の役割・状況は本人確認後に確定 |
| 3 | 実装を追う | エンジニアに具体的な技術事例の場所を案内 | Algomate、FingerDojoの事例リンク。技術名より「入力と結果」の説明を先に置く。主作品の技術事例と重複させない |
| 4 | その他の制作 | 代表作以外の経験を補完し、必要な読者に提供 | 公開状態・担当・説明価値を確認したサンプルだけ。タイトル、媒体、1文、外部リンク |
| 5 | プロフィールと連絡先 | 本人確認や追加情報への導線を提供 | 簡潔な自己紹介、GitHub/note、本人が希望・公開する場合のみ連絡先 |

## 代表作品ページの基本構成

見出しは閲覧者が知りたい内容を表し、「課題・判断・検証・振り返り」という固定テンプレートにはしない。各ページの冒頭に同じ情報ブロックを過剰に繰り返さず、概要の次に作品固有の説明へ進む。

| 順 | セクション | 採用担当者に見せる情報 | エンジニアが追う情報 |
|---|---|---|---|
| 1 | 作品名と一言 | ジャンル・特徴・状況 | 開発リポジトリへのリンク（公開可否確認後） |
| 2 | ゲームの入口 | 実画面または実際の紹介動画、操作／遊び方の短い説明 | メディアの対象バージョンと、説明対象の実装箇所 |
| 3 | 作品と本人の役割 | 個人/チーム、本人が担当した領域、制作状況、期間のうち確認済みのもの | 担当箇所のソースリンクと、そのページ内説明の範囲 |
| 4 | 作品の中心となる仕組み | この作品を遊びとして成立させるループ | 1つの具体的なコード事例、データから結果までの流れ |
| 5 | 画面に現れる実装 | 仕組みの挙動を示す実際の画面・画面キャプション | 対応する画像とコードのリンク。必要なら短い抜粋または図 |
| 6 | 関連資料 | ソース、README、プレイ／動画など必要なCTA | 詳細設計資料は補助リンクにまとめる |

「検証結果」は実施記録がある場合だけ掲載。「今後の課題」は作品紹介に必要で、本人の意図と裏付けを確認した改善方向がある場合のみ短く扱う。存在しないテスト・計測を空の項目として追加しない。

## 作品ごとのページ構成

### Kaomoji Clash（初版）— 代表ページの第一候補

1. **顔文字を組み立て、アリーナで戦う** — 画面とゲームの中心ループ
2. **パーツの構成がどう遊びに影響するか** — 確認済みのパーツデータ・ステータス計算を、1つの画面とデータ／コードへ関連付ける
3. **制作体制・担当・制作状況** — 本人確認した事実のみ
4. **関連リンク** — ソース、確認済みのWindows/Android配布先、紹介映像

現行ページのUnity Editorデータ作成映像は、ゲームプレイ紹介より優先度を下げ、必要ならデータ編集を説明する箇所に限定する。READMEに列挙された全システム・数値・将来方向は載せず、実際のコードと一致する1つのビルド処理に絞る。

### Bomb Crash — 代表ページの第二候補

1. **爆弾迎撃からWave攻略まで** — 動画またはゲーム画面、遊び方
2. **本人の役割とチーム体制** — 本人確認済みの担当を記載
3. **ルールからWaveを作り、敵を出す** — Wave設定→生成→進行→出現の図と、対応コードへのリンク
4. **画面上の結果** — 実画面でWave・敵・結果のどれを説明するか明示
5. **ソースとプレイ方法** — リポジトリを主CTAにする。配布版のリンクと動作対象を確認できるまでダウンロードを保証しない

ガチャ機能は未実装とREADMEが明記しているため、主要機能・完成度の根拠として見せない。短い作品ページに物語・各操作説明・全スキル一覧を重ねない。

## その他のページ構成

### Algomate Colony — コマンド実行の技術ケース

1. **ロボットに作業を指示するゲーム** — 動画または実画面、対象のプロトタイプ状態を本人確認後に記載
2. **1行の命令がどう処理されるか** — 入力→検証→逐次実行→ゲーム上の結果を1つの図でつなぐ
3. **対応するコードと画面** — 実際に対応する `CommandHandler`、`RobotCommandExecute` 等へのリンクと、命令画面／実行結果
4. **ソース・資料** — 現行仕様・実装状況のリンクは主紹介を補う資料群として末尾にまとめる

タイトルに「A*」「本格的な経路探索」「完全自動化」など、仕様資料で確認できない表現を使わない。現行資料にあるコマンド検証と実行の差・停止経路は実装範囲を決める証拠調査の論点であり、本人が説明・公開に同意するまで公開向けの「学び」として創作しない。

### 指道場（FingerDojo）— 短い戦闘ループ紹介

1. 実画面とゲーム概要
2. 指撃QTE、カウンター、休息のうち確認済みの一経路を図と画像で説明
3. 本人の担当、チーム表記、試作状態（確認後）
4. READMEまたは実装資料へのリンク

長い全クラス一覧、未実装の「技・煽り」を説明の中心にしない。現在の試作規模に合わせ、代表作ページより短くする。

### Kaomoji Clash / Reloaded — 開発中の記録

1. **制作中**の明確な表示と、実際に確認可能な短い紹介動画／画面
2. 初版から引き継いだもの／現版で変更したもの（同じゲーム概要は繰り返さない）
3. ソース上で確認できるドラッグ発射、Wave、成長のうち、1つの具体例
4. 初版へのリンクとコード

トップの代表完成作件数に含めず、制作途中かつプレイ・ビルド未確認の範囲を適切に伝える。現行ページの長い比較表や未検証事項リストは圧縮し、公開向けには簡潔なバージョン差分だけを残す。

### 技術サンプル・小作品

- タイトル、成果物の実形式（短い動画／GitHub／外部ゲーム）、何を実装したか1文、担当確認後の役割、外部リンクを1カードにまとめる。
- 実プロジェクトのコードや画面がない短い技術動画は、代表作品ページへ昇格させず、複数件を一つの補足一覧にする。
- 既存一覧の各サンプルの内容・担当・リンクを確認してから採否を決める。技術名だけで能力を断言しない。

### その他の公開ゲーム

Unityroom等の外部プレイリンクが現在も有効で、本人の担当を確認できた作品だけをタイトル＋遊べる入口の軽い一覧で紹介する。個別ページや内部設計解説は、実装の根拠・作品評価への寄与がある場合に限る。

## 削除・統合・縮小する項目

| 現行の要素 | 方針 | 理由 |
|---|---|---|
| トップの長い「強み」説明と各詳細への多数のリンク | 作品カードと直接つながる短い技術事例に統合 | 抽象的な自己評価の反復より、実物の作品・実装への導線を優先 |
| 「今後さらに伸ばしたいこと」3カード | トップの代表枠から外す。具体的な応募方針に有効な短い自己紹介が必要なら末尾に集約 | 作品より先に自己評価・未実施計画を長く置かない |
| サイドバーの作品ミニカード | トップと作品一覧から重複分を削る。詳細ページの末尾は「次の作品」リンク数件に限定 | 同じ作品への冗長導線とページの縦長化を避ける |
| 各ページで繰り返すゲーム概要・作品一覧・GitHub CTA | 1ページ内で一度ずつに統合 | 同じ情報・導線の反復で読解を阻害しない |
| 長いストーリー説明 | 基本は削除または関連資料に移す。ゲーム理解・本人貢献に直接必要な場合だけ1段落 | ゲームプログラマーとしての作品理解・実装根拠より優先度が低い |
| 網羅的な操作表・スキル／敵一覧 | 最初のプレイ理解に必要な操作だけ残す | マニュアルとポートフォリオの役割を分ける |
| 生の技術名・クラス名を並べた一覧 | 1つの機能に関係する名称だけを、流れ・画面・ソースに関連付ける | 採用側が構造や成果を理解しやすくし、技術用語の羅列を避ける |
| 「確認できたこと」「未検証・未計測」等の監査風公開見出し | 公開向けの自然な説明に書き換えるか、根拠がなければ省略。調査状態は内部資料へ | 内部レビューと採用プレゼンを分離する |
| Reloadedを完成作品と同列の代表作カード | 開発中の作品として別区分にする | 制作中・プレイ未確認のプロジェクトを完成作と誤認させない |
| FingerDojoの未実装コマンドを含む一覧 | 主説明から外し、現在確認した基本戦闘ループのみ扱う | UIに名前が残ることと機能実装を混同しない |
| 複数の長い関連資料ボタン | README・主要コード・必要な配布リンクへ整理し、詳細仕様書は二次リンクに集約 | 採用側の最初の選択肢を減らし、エンジニアの調査導線は保つ |
| コメントアウトされた動画制作カード | 現行表示には復活させない。工程1で別の強みを補う場合のみ採否を判断 | 現在の掲載対象でない素材を現行作品数と混同しない |

## 決定した設計判断と条件

- トップを「強みの長い説明」から始めず、制作者・代表作品・担当を早期に示す。
- 代表作品は **Kaomoji Clash（初版）とBomb Crashの2件を優先表示する案** とする。個人制作とチーム制作それぞれの実装例を提示し、AlgomateとFingerDojoは短い技術事例として位置付ける。
- この順序は公開README等からの暫定評価。プレイ可能性・担当範囲・証拠の明確さが確認できなければ再評価する。工程1の全作品評価と本人確認完了前には、実績・完成度を断定する文章を承認済みコピーとして扱わない。
- 完成作品の選定件数を「3作」など数字で断定せず、内容確定後に見出しを合わせる。
- 各ページの技術的説明は、画面または資料→機能の流れ→実ソースの順で対応付ける。存在するだけのコードや、今後作る図を現物のように説明しない。
- データや役割分担などのコード構造と、本人の意図・設計判断は区別し、後者は本人確認を要する。
- 配布ボタンは対象の実行ファイル、公開権限、起動確認、リンク到達性を確認できた場合のみ掲載する。
- この工程では情報設計を確定し、大規模なデザインやサイト実装には着手しない。

## 読者の到達性セルフチェック

### 採用担当者

- 1画面目で氏名・ロール・代表作へのCTAが見える。
- 代表作カードだけでゲームの軸、本人の担当、個人／チーム、制作状況が比較できる（担当・状態は本人確認後に掲載）。
- 2件の作品詳細で実画面と作品固有の強みが早く伝わり、コードを読まなくても実装内容の要約を理解できる。
- 技術サンプルや開発中作は代表作から視覚・情報上区別される。

### エンジニア

- 各代表作の技術事例から対応するデータ、処理経路、実ソースへ迷わず進める。
- 図や画像が実在の画面・処理と対応し、動作確認・配布確認・本人確認のない内容を保証しない。
- 詳細仕様書は補助情報へ整理し、最初から長文の仕様を読むことを要求しない。

**評価:** 提案した順序なら、採用担当者は「誰か→何を作ったか→担当は何か」をトップから短い経路で理解できる。エンジニアは代表作ページ内の1事例から画像・データ・コードへ段階的に掘り下げられる。担当範囲と実行・配布状態が未確認のため、これらの点が本人確認・作品実査で裏付けられることを構成確定の最終ゲートとする。
